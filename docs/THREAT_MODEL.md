# Threat model for 1.0

This model follows [heads-down.md](design/heads-down.md), especially §§2, 9–10 and 14–17. The supported deployment is a trusted local operator and MCP host on macOS or Linux, using one host per `ROUNDTABLE_HOME`. Provider services, repository content, model output and browser pages cross trust boundaries. An attacker may control repository files, issue bodies, plans, task cards, model replies or an outbound endpoint. The host OS, Docker daemon, installed CLIs and operator configuration are trusted; compromise of those invalidates the isolation assumptions.

**Implementation status:** security primitives, sandbox, execution store, contracts, leases, git hardening, watchdog, dashboard and GitHub sync exist in this tree. Worker drivers (`src/workers`), runner/CLI wiring and escalations are still in flight. Statements marked **Specified** refer to the approved design and require integration and release verification; they are not evidence that an absent module already enforces a control. Other references below identify existing code. The Docker sandbox contains commands, not the entire orchestrator or worker CLI.

STRIDE abbreviations: **S** spoofing, **T** tampering, **R** repudiation, **I** information disclosure, **D** denial of service, **E** elevation of privilege. Each boundary considers all six classes. Mitigations reduce risk; they do not make model judgments trustworthy.

## MCP host ↔ orchestrator server

Assets: tool authority, provider credentials, private prompts/personas, contract intent, budget and session state. The host launches `src/index.ts` over stdio; this is not a remote authenticated MCP endpoint.

| STRIDE / threat | Mitigations and references | Residual risk |
| --- | --- | --- |
| S: a caller claims to be the human or contract orchestrator | Local stdio process boundary (`src/index.ts`); `src/execution/contract-lifecycle.ts:freezeContractIn` checks the named orchestrator. | Names express authority within a trusted host; they are not independent authentication of a human. A compromised MCP host has the operator's tool authority. |
| T: malformed tool input changes scope or a stale vote freezes a new plan | `src/validate.ts:assertValid`, `src/tools.ts:checkArgs`, `src/execution/contract.ts:checkContract`; `src/execution/contract-state.ts:summarizeConsent` and lifecycle checks bind consent to version/hash. | Valid arguments may still express malicious intent. The host must preserve human intent. |
| R: callers deny authorizing a run or overriding consent | Existing freeze/amend audit entries (`src/execution/contract-lifecycle.ts`); **Specified** §13 records verbatim execution confirmation in event and audit logs. | Confirmation is a host-supplied statement, not a human signature; execution-tool wiring remains in flight. |
| I: prompts or keys leak through tool errors or concurrent sessions | `src/security/secrets.ts:scrubSecrets`, `src/agents.ts:loadAgent` containment, `src/sessions/lock.ts:withSessionLock`. | A permitted tool can send private context to the selected provider. Scrubbing is pattern/value based and incomplete. |
| D: overlapping turns, oversized requests or slow providers exhaust resources | `withSessionLock` refuses overlapping turns; schema bounds and `src/providers/retry.ts:withRetry` keep retries inside the call deadline. | Many separate sessions or large provider responses can still consume host memory and spend. |
| E: injected instructions turn a conversation into unrestricted execution | Contract validation, scoped authority in `src/execution/contract-lifecycle.ts:authorityNeeds`; **Specified** execute requires a frozen contract, human confirmation, budget and sandbox preflight (§13). | MCP host permissions and human review remain essential; annotations and prompts are not isolation. |

## Orchestrator server ↔ runner

Assets: run ownership, provider/git/GitHub credentials, frozen contracts, budget, worktrees and durable state. Both processes are trusted and run as the same OS account.

| STRIDE / threat | Mitigations and references | Residual risk |
| --- | --- | --- |
| S: a second process impersonates or steals a runner | **Specified** §2 uses `runner.lock`, host/pid ownership, heartbeat, stale-owner takeover and refuses a runner on another host. `src/execution/lock.ts:acquireLock` already protects store writes from live-owner displacement. | Runner ownership/preflight wiring is pending. A same-account attacker can replace private state. |
| T: concurrent writers or a torn append corrupt run state | `src/execution/store.ts` transactions validate/reduce a batch before append and fsync it; `src/execution/blackboard.ts:apply`; **Specified** resume verifies before reconciliation (§3). | Filesystem or host compromise can rewrite state and recompute hashes. |
| R: detached execution loses its authorization/history | `src/security/audit.ts:appendAudit`, `src/execution/chain.ts:hashEvent`; **Specified** confirmation, takeover and control events (§§2, 13). | Hashes are not external notarization. Runner process actions still need integration. |
| I: credentials reach the wrong subprocess or log | `src/security/child-env.ts:childEnv` profiles and `src/security/secrets.ts:scrubSecrets`; private files via `src/security/fs-safe.ts`. | The runner profile deliberately inherits the entire environment because it is trusted code and needs provider keys. |
| D: abandoned runners, overspend or stalled workers continue indefinitely | Existing `src/execution/watchdog.ts:evaluate`, budget/circuit/deadlock rules; **Specified** runner applies idempotent process operations and exits after six paused hours (§§2, 11). | Observations, enforcement and accounting depend on runner wiring; usage estimates can be inaccurate. |
| E: a lead widens scope or publishes directly to the base branch | `authorityNeeds` defaults to deny; child contracts fit parent paths/budget (`src/execution/contract.ts:childBudgetCap`). **Specified** completion opens an integration PR only, with human merge (§10). | The runner owns powerful credentials; operator-side branch protection and review are required. |

## Runner ↔ workers (`claude -p`, `codex exec`)

Assets: worker identity, leased paths, task branch, CLI credentials, tokens and command authority. Invocation, identity and attestation below are **Specified** in §9; the existing environment and sandbox primitives are building blocks, not a completed worker launch path.

| STRIDE / threat | Mitigations and references | Residual risk |
| --- | --- | --- |
| S: a worker emits events as another agent or reuses a token | **Specified** single-use 32-byte token file, unlink after reading, registered SHA-256 check, server-stamped identity, token rotation on resume (§9). | External workers receive trusted host-level access; a stolen token grants that worker's authority until rotated. |
| T: local CLI config adds tools/MCP servers or task text changes argv | **Specified** task cards on stdin; strict MCP config, generated settings, required-flag preflight and startup `system/init` attestation; kill/escalate unexpected tools or servers (§9). | Attestation relies on the CLI's truthful report and compatible CLI behavior; preflight cannot prove runtime isolation. |
| R: untraceable task edits and worker restarts | Existing `src/execution/worktrees.ts:commitLeasedPaths` adds execution/task/agent trailers; event types in `src/execution/types.ts`. **Specified** driver usage/session/exit recording (§9). | Trailers and events are local evidence, not signed worker statements. |
| I: workers inherit orchestrator keys or read private host files | `childEnv("claude-worker")` / `childEnv("codex-worker")`; **Specified** keyless MCP with `ROUNDTABLE_DOTENV=off`, secret-file read denies and restricted tools (§9). | CLI login/OAuth and selected cloud auth are intentional exceptions; API-key mode is opt-in. Codex workers have broader read scope and are opt-in. Neither environment filtering nor worktree cwd is an OS read boundary. |
| D: workers hang, fork helpers or consume excess budget | Existing `src/execution/watchdog.ts:evaluate`; **Specified** process-group termination, retries, CLI budget cap and admission gates (§§9, 11). | Provider billing and CLI cost reports may lag; worker process limits differ from Docker command limits. |
| E: worker shell bypasses command mediation | **Specified** Claude `--restricted`, explicit Read/Edit/Write/Glob/Grep tools, no Bash/WebFetch/WebSearch/Task, no extra MCP servers; commands only through sandboxed `run_command` (§9). Existing `src/sandbox/index.ts:runSandboxed`. | Codex retains its own sandboxed shell and checks leases only on submission. External workers are unsandboxed and trusted like the host chat. |

## Repository content ↔ workers (prompt injection)

Assets: task intent, private source/context, leased changes, validation results and the base branch. Treat repository files (including instructions and scripts), GitHub issues, plans and task cards as potentially hostile data. A prompt instruction cannot confer authority.

| STRIDE / threat | Mitigations and references | Residual risk |
| --- | --- | --- |
| S: repository prose impersonates the human, lead or a tool response | **Specified** generated task protocol and worker-bound MCP identity (§9); existing `src/execution/contract-lifecycle.ts:authorityNeeds` checks privileged changes against contract authority. | Models can still confuse quoted instructions with trusted directives. |
| T: injection edits unrelated paths, hides renames or replaces checks | `src/execution/leases.ts:pathCovered`, `src/execution/worktrees.ts:checkLeaseCoverage` check both rename sides; explicit leases for `.git*` metadata; nested repositories refused; every symlink in the proposed tree is resolved hop by hop through the git tree itself (`unsafeTreeSymlinks`, `symlinkEscapes`), and chains that leave the worktree, dangle, touch `.git`, or exceed 40 hops are refused before commit and before merge. **Specified** PreToolUse hook checks live leases before Edit/Write/NotebookEdit (§9). | Hooks depend on the worker driver. Symlink checks validate the committed tree, not later filesystem state: a link changed between check and use on the host is outside this guarantee (sandboxed commands can't write `.git`, and host git reads committed objects). Leased changes can be malicious. |
| R: a task submits false progress or a forged successful test report | Existing store validation and hash chain; `src/execution/merge.ts:mergeTask` checks coverage; **Specified** runner performs task, integration and final validation (§10). | Model assertions are untrusted; tests can miss malicious behavior or be changed within an authorized lease. |
| I: instructions exfiltrate context through commands or public output | **Specified** no Bash, `--restricted`, tool attestation and sandboxed `run_command`; existing Docker commands default to no network (`src/sandbox/docker.ts:buildDockerRunArgs`), public redaction (`src/publishers/redact.ts:redact`). | Workers send context to their model service; redaction misses unusual secrets. Allowed install hosts may be exfiltration channels. |
| D: hostile scripts loop, fork or generate huge output | `src/sandbox/docker.ts` resource limits, `src/sandbox/common.ts:OutputCapture`, `src/execution/watchdog.ts:evaluate`. | Prompt-induced wasted work/spend persists within caps; local commands lack Docker's resource limits. |
| E: injected text escapes tool limits or lands malicious code automatically | **Specified** hook, restricted tool set and attestation (§9); existing sandbox and hardened git. **Specified** final human review/merge: never auto-merge and never push to the base branch (§10). | Prompt injection is not solved. A human may approve a harmful diff; Codex and external workers have the broader authority described above. |

## Sandbox ↔ host

Assets: host files and credentials, git administrative state, host network, kernel resources and command output integrity.

| STRIDE / threat | Mitigations and references | Residual risk |
| --- | --- | --- |
| S: command substitutes another checkout or git directory | `src/sandbox/common.ts:canonicalWorkdir` refuses symlinked workdirs and `.git`; `src/execution/git.ts:openLinkedWorktree` verifies gitfiles against the main repository's records. | Host-account adversaries and filesystem races exceed the single trusted operator assumption. |
| T: command rewrites host git config/hooks or uses a nested repository | Docker mounts `/work/.git` read-only; `src/execution/git.ts:GIT_HARDENING` disables hooks, fsmonitor, external diff/textconv, signing, maintenance and transports. `assertNoGitlinksInTree` / `assertNoGitlinksInIndex` refuse submodules in base/index/HEAD/merge inputs; host git never enters nested repositories. `src/execution/worktrees.ts:commitLeasedPaths` never stages nested repositories or `.git` paths. | Filter/merge drivers defined in the user's own global config may still execute on the host when `.gitattributes` names them. Such metadata needs an explicit lease. |
| R: an unsafe fallback is hidden from the operator | `src/sandbox/index.ts:selectBackend` requires local opt-in and returns degradation reasons; result records backend/image digest. **Specified** runner emits `sandbox.degraded` (§16). | Persisting and displaying degradation depends on caller integration; ignoring it accepts reduced isolation. |
| I: commands read host secrets or contact internal services | `buildDockerRunArgs`: only worktree mounted, read-only root, temporary HOME, validated environment, `--network none`. Install-only egress uses `src/sandbox/egress-proxy.ts:ensureEgressNetwork`: internal Docker network, allowlisted DNS names, CONNECT to 443 only, all resolved IPs public, connect to a checked IP. | Secrets already in the worktree remain readable. The proxy does not inspect TLS, SNI, paths or payloads: it is a destination allowlist, not content inspection. |
| D: fork bombs, memory exhaustion or unbounded command output | Docker `--pids-limit`, CPU/memory/no-swap limits, tmpfs cap, no host container log; `src/sandbox/process.ts:spawnCaptured` timeout/process-group kill; output capped and scrubbed by `runSandboxed`. | Docker/OS vulnerabilities remain; local backend has no CPU, memory or process-count limits. |
| E: root/capability abuse or local fallback escapes confinement | Docker non-root uid, `--read-only`, `--cap-drop ALL`, `--security-opt no-new-privileges`, no Docker socket mount (`buildDockerRunArgs`). macOS `src/sandbox/local.ts:buildSeatbeltProfile` denies network, outside writes, workdir replacement, `.git` writes, selected credential reads, outside signals and keychain/launch/clipboard services. | Local is weaker than Docker: macOS permits other outside reads and worktree secret reads; Linux `unshare -rn` isolates only network and leaves files/`.git` writable. If unavailable, execution may be wholly unisolated with a degradation reason. Local has no install egress support. |

Submodules are unsupported in 1.0 heads-down runs. A nested `.git` must never become an alternate trusted host-git context; untracked nested repositories are listed and refused for staging rather than recursively inspected. Container images, registry packages/install scripts and the Docker daemon remain trusted dependencies. Review image digests and minimize allowed install hosts.

## Outbound network: providers, ntfy/webhooks and GitHub

Assets: provider and publisher keys, GitHub authority, private prompts, public text/attachments and internal network services.

| STRIDE / threat | Mitigations and references | Residual risk |
| --- | --- | --- |
| S: an attacker-controlled provider origin receives the configured API key | `src/providers/openai-compatible.ts:createOpenAICompatibleCall` binds keys to configured/trusted origins; untrusted per-call overrides are guarded and receive no key. `src/providers/shared.ts:assertNotRedirect` refuses redirects. | Operator-configured provider URLs and explicitly trusted origins are trusted configuration, not all guarded like untrusted overrides. A malicious trusted origin receives its key and prompts. |
| T: a URL redirects to metadata/private services or a GitHub marker is forged | `src/security/url-guard.ts:guardUrl` rejects userinfo and metadata, checks every DNS answer, requires HTTPS except loopback/explicit private allowance. Webhooks recheck every send and use manual redirects (`src/publishers/webhook.ts:WebhookPublisher`). `src/github/sync.ts:GitHubSync` trusts markers only on the authenticated account's labelled issues/comments, using GraphQL identity. | URL guard has a DNS rebinding TOCTOU: fetch resolves again after validation. Webhooks deliberately allow private LAN targets and HTTP there; configure them carefully. |
| R: retries duplicate external actions or publication failures disappear | `GitHubSync` atomically persists cursor/outbox and event markers; `src/publishers/queue.ts` tracks delivery and retries; local transcripts record delivery state. | Remote service retention/deletion and failures before acknowledgment prevent a complete independent delivery record. |
| I: public posts leak secrets/PII or trigger notifications | `src/publishers/redact.ts:redact`; `src/github/sync.ts:ghText` redacts and breaks mentions/references/URLs, never publishes diffs or command output. Webhooks send attachment metadata only; prototype source is redacted before screenshots. | ntfy links are publicly readable; attachments/transcripts may outlive local runs. `src/publishers/ntfy.ts:NtfyPublisher` uses trusted configured HTTP(S) URLs, does not use the URL guard and uses fetch's default redirects. It lacks the webhook's metadata/private-address checks and manual-redirect policy. Use a trusted HTTPS ntfy origin; do not assume equivalent SSRF or credential protection. |
| D: hung services, quotas or retries block progress | Provider deadlines/backoff (`src/providers/retry.ts:withRetry`), publisher queues, GitHub token buckets/backoff and degraded reporting (`GitHubSync:syncOnce`); `src/github/gh.ts:runGh` has a 30 s timeout and output cap. | Providers still charge for work; remote outages and rate limits reduce visibility. |
| E: injected issue content executes host commands or abuses GitHub permissions | `runGh` uses argv, `childEnv("gh")`, GraphQL and 0600 body temp files (`withBodyFile`); `ghText` escapes untrusted content. **Specified** sync is optional, never merges to base (§14). | `gh` credentials retain their configured repository/project authority. CLI config/proxies and provider services are trusted; least-privilege account setup is the operator's job. |

## Dashboard ↔ browser

Assets: run status, contract, private diffs/output, capability token and browser origin. The dashboard is a read-only loopback view; it is not a hosted user account system.

| STRIDE / threat | Mitigations and references | Residual risk |
| --- | --- | --- |
| S: a hostile site guesses the capability or uses DNS rebinding | `src/http/secure-server.ts:newCapabilityToken` uses 18 random bytes; `tokenMatches` compares SHA-256 digests in constant time; `SecureServer` checks Host and binds to 127.0.0.1. Missing/wrong tokens yield the same 404. | Anyone who obtains the URL can read it; same-account processes or browser extensions may steal it. No per-user authorization. |
| T: event text becomes XSS or forged links | `src/dashboard/render.ts` redacts/escapes run text; `markdownToHtml` passes no raw HTML or links. `src/dashboard/server.ts:DASHBOARD_CSP` allows only self scripts/styles; assets are separate routes, no inline scripts or handlers. | Rendering and browser vulnerabilities remain possible. Prototype app frames use a separate sandboxed opaque-origin policy that permits inline app scripts; it is not the dashboard policy. |
| R: a browser silently mutates state and denies doing so | `SecureServer` accepts GET/HEAD only and refuses CONNECT/upgrades/proxy requests; dashboard exposes no mutating routes. Control stays in MCP tools. | Viewing is not attributed to an individual or audited as a user session. |
| I: secrets leak through HTML, state polling, referrers or browser cache | `src/dashboard/render.ts:publicState` omits diffs/output/blobs from polling; full pages redact; `COMMON_HEADERS` uses no-store, no-referrer, nosniff and framing/origin protections. Token is not logged by the server. | Human-visible diffs can contain unrecognized sensitive text; `dashboard.json` intentionally stores the capability URL in the private state directory. |
| D: unlimited connections or event streams exhaust resources | `SecureServer` connection cap; dashboard stream limit, bounded diff/output and paginated events (`src/dashboard/server.ts`). | A local attacker can still consume host resources; this is not an internet-facing hardened service. |
| E: browser invokes runner actions or reaches the host network | Read-only routes and CSP `connect-src 'self'`, `form-action 'none'`, `frame-ancestors 'none'`; no browser control API (`startDashboard`). | Host malware and privileged browser extensions are outside this boundary. Capability access reveals data but should not authorize run control. |

## Local filesystem

Assets: credentials, contracts, worker tokens/configuration, event/audit logs, snapshots, blobs, worktrees, archives and public transcripts.

| STRIDE / threat | Mitigations and references | Residual risk |
| --- | --- | --- |
| S: predictable IDs or symlinks redirect access to another record | `src/ids.ts:newId` / `newExecutionId` use cryptographic randomness; `src/security/fs-safe.ts:mkdirPrivate` refuses a symlink at its final path; agent refs use realpath containment (`src/agents.ts:loadAgent`). | IDs are not authentication. Parent directories and OS-account integrity must be trusted. |
| T: partial writes, concurrent transactions or edited logs corrupt state | `writeFileAtomic` uses exclusive sibling temp files, fsync, rename and directory fsync; store locks, strict validation, complete-batch replay, content-addressed blobs and snapshots. `src/execution/verify.ts:verifyExecution` and `src/security/audit.ts:verifyAudit` verify hash chains. | Hash chains are tamper-evident, not tamper-proof. An attacker who can rewrite the chain and its anchor can recompute it; suffix deletion without an external trusted head is not generally detectable. |
| R: security actions or old audit history vanish unnoticed | `appendAudit` links across monthly files. `pruneAudit` writes `audit-anchor.json` before deleting whole old months and records `audit.pruned`; `verifyAudit` requires the remaining head to link to the anchor or genesis. | A malicious same-account writer can replace logs/anchor together. There are no signatures or external immutable checkpoints. |
| I: world-readable state or retained blobs expose private context | `mkdirPrivate` 0700, `writeFileAtomic`/store files 0600; free-text secret scrubbing before hashing; `src/execution/blobs.ts:scrubbedJSON`. **Specified** all entry points set umask 0077 (§2). | No at-rest encryption; paths/identifiers are stored as given. Scrubbing cannot identify every confidential value; backups and public transcripts need their own policy. |
| D: logs/blobs grow without bound or pruning removes active work | **Specified** retention is 30 days after runs end, 365 days for audit (§16). Existing `pruneAudit(365)` preserves the newest month; `src/sessions/archive.ts:pruneArchivedSessions(30)` handles dated archives. | Execution retention scheduling is still in flight; archive pruning is not wired in. No automatic retention guarantee yet. Disk exhaustion and operator deletion can stop a run. |
| E: permissions or worktree metadata grant access to other accounts | Private modes, normalized relative paths (`normalizeRelPath`) and git/lease controls above; **Specified** token files are single use (§9). | Root and the same OS account can read/replace these files. Multi-user or hosted isolation, Windows heads-down runs and shared multi-host state are unsupported. |

## Verification and release obligations

Tests in `test/unit/security-primitives.test.mjs`, `url-guard.test.mjs`, `scrubbing.test.mjs`, `security-audit.test.mjs`, `execution-*.test.mjs`, `sandbox-*.test.mjs`, `http-secure-server.test.mjs`, `dashboard.test.mjs` and `github-sync.test.mjs` exercise the existing boundaries. [SECURITY_CONTROLS.md](SECURITY_CONTROLS.md) maps individual safeguards to evidence. Recheck the specified controls against merged worker/runner/escalation code and end-to-end tests before declaring 1.0 ready. Complete the marked action pins before merging the supply-chain workflows; local offline validation cannot establish registry audit or hosted CodeQL/publishing results.
